# Welcome Bot — Storage Update Manager 1.1

## Статус

Кандидат подготовлен локально 14.10.2026. Production НЕ изменён; отправки в Telegram не выполнялись. Для установки нужно отдельное разрешение владельца.

## Аудит

Снят исходный Welcome_Bot.py из работающего контейнера `welcome-telegram-bot` (не из устаревшей GitHub-копии). Python 3.13, aiogram 3.31.0, aiohttp 3.14.4, polling. Реестр пользователей — JSON в `/data/user_registry.json`. Контейнер UID 10001, read-only root, 256 MiB, 0.25 CPU, volume `/srv/storage/telegram/welcome-telegram-bot:/data`. Код приветствий/правил/модерации сохранён. Изменения только: регистрация шести обработчиков перед catch-all F.text и добавление фоновой задачи в существующий lifecycle.

Фактические объекты расположены в Contabo `novaryn-storage`, префикс `Для канала/`. Директория VPS не содержит эти файлы. Поэтому выбран API завершённых объектов хранилища, без сканирования VPS, монтирования административной SQLite или передачи S3 credentials боту.

## Механизм

API использует индекс только завершённых объектов. Multipart не появляется в индексе до завершения; активная замена помечается busy. Бот требует два стабильных наблюдения с интервалом 15 s и дополнительный HEAD через защищённый API, проверяющий размер и ETag. Через 60 s после последнего подтверждённого события публикует пакет. Новые кандидаты/активные загрузки откладывают пакет; через 600 s публикуются только завершённые файлы. При недоступности источника приоритет — корректность, а не точный срок.

Одинаковый stable ID и ETag/размер при переименовании не являются обновлением. Удаления не публикуются. Изменившийся ETag/размер — замена. Одинаковое содержимое с тем же ETag не вызывает нового поста. Первый запуск и повторное включение создают baseline без старых публикаций. Во время отключения события не копятся для последующего спама.

Состояние: `/data/storage_updates.json`, 0600, атомарная замена + fsync. Отдельная SQL-база не нужна: Welcome Bot использует JSON. Реестр пользователей не изменяется. Pending/outbox восстанавливаются после рестарта; повреждённое состояние не сбрасывается автоматически. Хранятся последние 100 публикаций/ошибок; /storage_history показывает 10. Незавершённые и неоднозначные задания не удаляются автоматически.

## Telegram и пределы гарантии

Целевой чат из ранее предоставленного владельцем ID: `-1001938728395` (платная группа обсуждений). ID канала `-1002382367995` НЕ используется. Перед каждой отправкой getChat должен вернуть group/supergroup. Используется только существующий Bot и BOT_TOKEN. /storage доступна в целевом чате и личных сообщениях; другие команды требуют ADMIN_IDS + текущий статус administrator/creator именно целевой группы.

Telegram не предоставляет idempotency key для sendMessage/sendPhoto. 429 автоматически повторяется с retry_after. Сетевые ошибки предварительной проверки безопасно повторяются. Timeout/5xx во время самой отправки и процесс, прерванный в sending, переводят задание в uncertain: повтор может создать дубль, поэтому автоматического повтора нет. Это отображается в /storage_status, с ограниченным кодом в error history. Оператор сверяет чат и вручную решает судьбу задания в закрытой копии state после остановки только бота. Нельзя обещать exactly-once при таких сбоях.

Если Pillow не создал обложку, выполняется одна текстовая отправка. После сетевой ошибки отправки фото текстовый fallback НЕ выполняется, чтобы избежать двух постов. /storage_test отправляет явно помеченный тест в настроенную группу, не меняя хранилище.

## Развёртывание ПОСЛЕ разрешения

1. Сохранить текущие image ID, compose/.env и согласованную копию `/data` Welcome Bot. Сохранить образ/Compose текущего хранилища. Не выводить секреты.
2. Создать отдельный случайный `STORAGE_EVENTS_API_TOKEN` (не менее 32 символов). Сохранить один и тот же токен в закрытых env-файлах двух сервисов (root:root, 0600). Это ограниченный ключ чтения метаданных, не Telegram/S3 token.
3. Включить в образ хранилища API-патч. Добавить `STORAGE_EVENTS_API_TOKEN` и `STORAGE_EVENTS_ALLOWED_PREFIXES` из примера. Без токена маршрут отвечает 404. С токеном доступны только три явно разрешённые категории; скрытые/приватные/конфигурационные/временные файлы фильтруются на обеих сторонах. Никаких новых публичных портов.
4. Собрать образ бота: `docker build -t technology-universe-welcome:storage-update-manager-1.1 .`. Проверить итоговую версию aiogram: 3.31.0. Использовать существующую сеть/volume/токен. Overlay применять к оригинальному compose, а не как отдельный проект.
5. Скопировать `storage.env.example` в `storage.env`, заполнить ключ. `STORAGE_NOTIFICATIONS_ENABLED=false` оставить выключенным. STORAGE_WATCH_PATH здесь — логический S3-префикс, не каталог ОС. Монтировать файлы хранилища боту не нужно: используется HTTPS API только для чтения.
6. Пересоздать только контейнер хранилища и существующий `welcome-telegram-bot`; другие контейнеры не трогать. Не запускать параллельный экземпляр бота.
7. Проверить core healthcheck, /version, /health, приветствия/правила в согласованном тестовом чате. Выполнить /storage_status в личных сообщениях администратора. Убедиться, что baseline готов.
8. После подтверждения назначения отправить /storage_test, проверить HTML, обложку/кнопку именно в группе. Выполнить /storage_enable и реальную загрузку тестового файла через сайт; ожидать один пост. Затем проверить замену/пакет/перезапуск. В данном локальном этапе реальные сообщения не отправлялись.

## Откат

/storage_disable прекращает новые автоматические публикации и отменяет ещё не отправленные задания. Дождаться завершения текущего запроса. Сохранить state и журнал; затем вернуть прежние image/compose Welcome Bot. API-патч хранилища можно оставить выключенным (убрать токен) либо вернуть прежний образ. Исходные файлы Contabo и пользовательский реестр не изменялись. Не восстанавливать старую state-копию поверх актуальной без сверки message_id: это может повторить публикации.
